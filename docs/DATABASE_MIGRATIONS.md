# Database Migrations

## Purpose

SetPilot now includes Alembic migration tooling so database schema changes can be reviewed and applied deliberately. This is preparation for Phase 2 cloud staging. It does not connect the app to Supabase yet and it does not remove local SQLite support.

The current FastAPI app still runs `Base.metadata.create_all()` at startup for local prototype compatibility. Alembic is the migration path going forward, and later cloud sprints should move staging databases through Alembic instead of relying on startup table creation.

## Local SQLite Role

Local development still defaults to SQLite:

```text
sqlite:///./setpilot.db
```

You can keep running the backend locally without cloud accounts. Existing local SQLite files are not deleted automatically. If you intentionally reset a prototype database, do that manually and only after confirming you do not need its data.

## Future Supabase PostgreSQL Role

Supabase PostgreSQL is planned for a later Phase 2 sprint. Sprint 4 only adds migration infrastructure and an initial schema migration. Do not paste real Supabase connection strings into committed files.

When Supabase is introduced, `DATABASE_URL` should be set in the backend hosting environment only.

## Common Commands

Run commands from the backend directory:

```powershell
cd backend
.\.venv\Scripts\activate
```

Check current migration status:

```powershell
alembic current
```

Show migration history:

```powershell
alembic history
```

Apply all migrations:

```powershell
alembic upgrade head
```

Create a new autogenerated migration:

```powershell
alembic revision --autogenerate -m "describe change"
```

Autogenerated migrations must always be reviewed manually before commit. Check table names, column nullability, indexes, foreign keys, and downgrade behavior.

## Environment Variables

Alembic uses the same database URL resolution as the app:

1. `DATABASE_URL`
2. `SETPILOT_DATABASE_URL`
3. local default `sqlite:///./setpilot.db`

Do not commit real database URLs, passwords, Supabase URLs, or cloud secrets. Keep real values in local shell variables or deployment dashboards.

PowerShell example for local SQLite:

```powershell
$env:DATABASE_URL="sqlite:///./setpilot.db"
alembic current
```

Placeholder-only future PostgreSQL example:

```powershell
$env:DATABASE_URL="postgresql+psycopg://setpilot_user:replace_me@db.example.invalid:5432/setpilot"
```

## Safety Rules

- Do not run destructive migrations blindly.
- Do not drop tables or columns without a data-retention decision.
- Do not edit an already-shared migration after it has been applied elsewhere; create a new migration instead.
- Do not commit real `DATABASE_URL` values.
- Keep local SQLite and future PostgreSQL behavior in mind when reviewing generated operations.

## Current Sprint 4 Boundary

Sprint 4 adds Alembic configuration, an initial schema migration, and documentation. It does not remove `create_all`, does not connect to Supabase, and does not add authentication or user-owned data.
